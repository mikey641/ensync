# Architecture

The UI is a React/Vite prototype. A production build should use a small native desktop shell and a separate Ensync Host runner.

## Boundaries

1. The desktop app owns windows, tabs, preferences, credential prompts, and local project selection.
2. Ensync Host owns CLI discovery, process isolation, subscriptions, job queues, usage telemetry, and encrypted remote access. Installing a Windows client through Microsoft Store does not move execution or provider credentials away from the selected local or remote Host.
3. Agent adapters normalize streaming events, session IDs, limit/reset signals, tool calls, and final responses.
4. The router retries another subscription only for availability, authentication, quota, or capacity failures. It must not replay after a mutating tool call.
5. The context compiler reads `.ensync` and emits thin provider-specific instruction files without duplicating durable project facts.
6. Telegram is a restricted client of Ensync Host, not an independent model transport.
7. Ensync Sync is an optional account service for encrypted conversation documents. The local Host owns login, encryption/decryption, and revision handling; the remote service owns password verification and opaque ciphertext storage. It never becomes an execution target and cannot supply CLI credentials, provider sessions, or machine verification.
8. Provider integration is capability-driven and catalog-wide. Shared Host contracts cover discovery, account authentication, billing/overage guards, structured events, sessions, permissions, cancellation, usage, updates, local/remote execution, and both desktop platforms; provider-specific adapters may report an unsupported capability but may not silently disappear from a provider-facing change.
9. Coding providers never run in the user-selected shared checkout. The exact pinned `agent-worktree` runtime creates or reuses one stable branch and worktree for each conversation. The singleton Host uses a process-local owner check to reject a duplicate run for the same workspace immediately; it never creates filesystem workspace leases, heartbeat timers, lock polling, or stale-lock quarantine. Different conversation worktrees in one repository run concurrently.

Project isolation fails closed before provider execution when Git, an initial commit, or a consistent managed worktree cannot be verified. Uncommitted changes in the shared checkout do not block chat creation: the agent works in an isolated worktree branched from HEAD and never sees or touches those changes. It never cleans, stashes, synthesizes hidden history from a dirty checkout, or mutates the shared checkout to admit a provider. The landing integrator has its own clean-checkout guard that waits until the user has committed or stashed before merging agent work back into the target branch. Legacy registered `ensync/chat-*` worktrees remain adoptable so upgrades do not orphan work.

After a successful local provider turn, the Host verifies that the conversation branch and common Git directory did not change, commits a clean exact workspace state, anchors that SHA under `refs/ensync/landing-snapshots/`, records it in a checksummed landing journal, and completes the provider job without waiting for integration. Each prompt captures the workspace's delivery destination when it is sent. The default **Production** destination starts the background coordinator on the next microtask; **Protected branch only** records a terminal held delivery and never merges, pushes, or deploys it. Production deliveries run one FIFO train per shared Git directory and batch completions that arrive during an active train into the next train. A tool-owned integration worktree starts from an immutable ref for the inspected target SHA, applies each exact saved SHA through `agent-worktree`, and runs dependency-free structural and ancestry checks. The pinned open-source tool then publishes one no-force merge commit to the explicit checked-out target under an expected-old reference-transaction guard; post-publication checks stay pinned to that one resulting SHA and verify the final ref. Repository package scripts never run. After a successful train landing, the coordinator auto-pushes the target branch to origin with the same no-force policy; a push failure does not undo the local merge. Conflict resolution is offered only to a catalog provider whose automatic-landing capability is explicitly `supported`, whose subscription authentication is verified, and whose runner has the required containment boundary. Each resolver uses its account-selected model at the strongest verified reasoning effort for that runner; failed attempts are discarded with the temporary integration worktree, rotate across eligible providers, and retry durably after 1 second, 5 seconds, 30 seconds, 2 minutes, then every 10 minutes until one passes the landing checks. Later compatible items may proceed during the backoff. The integrator never checks out an entire `ours` or `theirs` side, regardless of attempt count. There is no manual `Needs merge review` state. Startup recovery resumes journaled queued/retry entries without replaying a provider prompt.

Provider maintenance is also Host-owned. The renderer may request only a catalog provider ID, whether to launch or preview, and the fixed manual/automatic trigger kind; the Host resolves the installed executable and fixed provider-owned update arguments. It refuses update launches while Host-owned agent jobs are active, deduplicates concurrent automatic launches across native windows, and never infers that a newer version exists from package registries. Every installed catalog provider participates in the device-wide maintenance policy: the default weekly reminder reviews them all, while opt-in automatic mode opens every verified self-update command when the Host is online and idle, recognizes providers whose own background updater is authoritative, and flags installation-method/platform-dependent providers for their official guide. It never launches an agent session merely to trigger a background update and does not claim completion that the Host cannot observe.

Production delivery is a second Host-owned state machine after landing. It journals the exact pushed SHA, polls an adapter for that exact production artifact, and reports Saved/Landing/Pushed/Building/Production to the renderer. The delivery record carries the prompt's stable turn identity and the landing coordinator's exact queued/integrating/retry/landed substate; the renderer resolves the human-readable prompt description from its own chat transcript, while a published merge subject becomes the durable description. Raw prompts never enter the landing or delivery journals. A failed deployment is deduplicated against a currently running project chat; otherwise it becomes an isolated max-effort subscription repair job with provider rotation and durable backoff. A new successful repair commit does not close the incident merely because it landed or built: Git ancestry must connect it to the failed SHA and the adapter must independently report that exact replacement as production. Deployment credentials and raw logs stay Host-side; only redacted bounded status reaches the renderer.

The subscription bridge pattern is based on the proven queue-and-runner separation in `../nadlan-desk/worker/src/subscription-agent.ts` and `project-agent.ts`.
