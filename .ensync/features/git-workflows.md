# Git workflows

Ensync Host owns Git operations for the focused local project. The browser never builds a shell command and never collects or stores a Git service token. The host launches the fixed `git` executable with a separate argument array and relies on the computer's existing Git credential helper or SSH agent.

## Agent workspaces

Coding agents do not mutate the focused shared checkout. For each stable workspace/conversation key, Ensync Host creates or reuses a durable `ensync/chat-…` branch in a managed Git worktree, maps a selected repository subdirectory to the same location inside that worktree, and reports the protected identity in the conversation. Git before/after continuation status is read from that worktree. The selected canonical path remains the project identity for navigation and explicit user Git operations.

The renderer persists an explicit `conversation:<chat-id>` agent-workspace key on the conversation before starting local or SSH execution. Chats already bound to a worktree under the former object-coerced key keep that exact key so an upgrade cannot orphan their branch or continuation state. A request with no key indicates a mixed-version client and fails before provider execution with an actionable quit-and-reopen upgrade error; malformed supplied keys still fail validation.

The pinned open-source `agent-worktree` CLI owns creation and durable location of new conversation worktrees. Ensync pins its private runtime config to empty hooks, empty copied files, and disabled automatic submodule cloning, because upstream 0.13.6 otherwise permits unbounded unsandboxed hooks and network cloning during these operations. Since that release has no per-command switch that can disable project config, a repository containing `.agent-worktree.toml` fails fast before `wt new` or `wt sync` rather than executing it with Host authority. Native worktree commands are serialized only around this shared config's refresh-and-use interval; provider work in different worktrees remains concurrent. The singleton Host keeps only a process-local owner map so a duplicate run for the exact same conversation fails immediately instead of waiting. A dirty canonical checkout blocks creation before the provider starts and remains byte-for-byte unchanged. Ensync does not create filesystem workspace locks, poll for lock release, synthesize a transport commit, or merge a new shared baseline during admission. Existing registered legacy `ensync/chat-*` worktrees and branches are adopted non-destructively. Managed worktrees and branches survive run completion and failure.

## Automatic landing

Automatic delivery continues beyond Git push. The Host persists the exact pushed production-branch SHA in a separate checksummed journal and observes that exact commit through a deployment adapter; a merely newer or older successful deployment never certifies it. Vercel projects use the linked `.vercel/project.json` plus the locally authenticated Vercel CLI REST credential, which remains Host-only and is never journaled or returned to the renderer. The adapter honors the CLI credential's second-based expiry, silently rotates an available refresh token through Vercel's discovered OAuth endpoint, persists the rotated pair with owner-only permissions, retries the exact lookup, and falls through to another configured credential after an authentication rejection. The visible lifecycle is **Saved → Landing → Pushed → Building → Production**, shown in a collapsed-by-default disclosure beside the chat's CLI execution panel. Landing is refined with the exact coordinator state: waiting for merge, merging by Ensync, retry scheduled, or merged awaiting push. Each record carries the originating turn ID, and expansion labels it as the running, previous, latest, or earlier prompt and shows a bounded description from the local conversation; the journal never stores raw prompt text. Once Git publishes the landing, its readable merge subject becomes the durable description and is backfilled for older records when the exact commit remains available. The collapsed state visibly identifies itself as this chat's result; expansion names the chat and exact protected source branch, and labels its external target as this chat's deployment. Each protected conversation requests only records whose journaled source branch exactly matches that conversation; a project-wide status must never leak another chat's delivery into the pane. The renderer repeats this exact-branch filter and fails closed when an older still-busy Host ignores the new request field during a rolling update. Expansion persists independently per stable chat and does not change as delivery advances. On startup and status reads, the Host recovers the current production-branch head and verifies it independently, so older production remains visibly live while newer saved work is reported separately as landing/building. Missing adapter/authentication is labeled unavailable and retried; it is never presented as production.

An unlinked active Host turn is always the delivery disclosure's primary subject, including when another window owns the run and the local renderer's sending flag is false. After the turn ends, the latest user prompt remains the disclosure's primary subject with its terminal run status instead of disappearing behind delivery history. A saved or production record belongs to that run only when the Host journal carries the exact turn ID and, for production, Git proves the saved commit is an ancestor of the exact deployed commit. The renderer never repairs or guesses this relationship from transcript text, CLI notices, timestamps, or SHA prefixes. New saved commits redundantly carry a bounded `Turn-ID` trailer; the Host can backfill a legacy landing item only from its exact immutable commit metadata after provider and protected-branch validation, then persists that proof in both journals. Multiple user instructions steered into one provider turn are labeled as one run rather than falsely assigning its shared commit to one prompt. Until an active turn is saved, the collapsed header says it is running and not saved.

Settings exposes a workspace delivery destination captured separately for every prompt, including queued prompts. **Production** is the backward-compatible default and performs the full automatic merge, push, deployment observation, and repair flow. **Protected branch only** saves and anchors the exact commit as a terminal held item but never merges, pushes, or deploys it; already-saved work keeps its captured destination when the setting changes. This is the only provider-neutral non-production option: Ensync does not claim a staging or preview deployment unless a project explicitly configures one.

A failed exact deployment becomes one durable repair incident. If a local chat for that project is already running, the incident attaches to that owner and does not launch duplicate work. Otherwise the Host starts a new isolated subscription-backed repair job using the originating eligible provider first, then rotates through the other verified automatic providers. Each repair keeps the provider's account-selected default model, requests its verified `max` effort, redacts and bounds deployment logs, and may not bypass build, schema, security, or deployment gates. Failed repair attempts use 1 second, 5 seconds, 30 seconds, 2 minutes, then 10-minute retries indefinitely. A repair is complete only after a descendant replacement SHA is independently observed as the exact successful production deployment. Host startup resumes incomplete delivery records, and delivery monitoring keeps the daemon busy without converting Host shutdown into a user cancellation.

A successful local turn is committed on its conversation branch and identified by that exact immutable SHA. Before delivery, the Host compares the exact run-start and final source trees; a successful informational or no-op follow-up creates no landing item and leaves the prior delivery attached only to the run that produced it. Both landing and delivery journals enforce one originating run per saved commit, and startup removes ambiguous later duplicates written by older Hosts while retaining the earliest durable identity. The Host atomically appends a changed item to a checksummed landing journal, then marks the provider job complete immediately; repository integration never extends the chat spinner or pins the provider process.

The event-driven coordinator maintains one completion-order FIFO train per repository. The first completion starts integration on the next microtask. Completions arriving during that train are batched into the next train, while different repositories integrate concurrently. Each train gets a separate tool-owned worktree pinned to the inspected target SHA, applies item SHAs in order with `agent-worktree`, and verifies exact SHA and original-target ancestry, a clean index, conflict markers, and `git diff --check`. The pinned tool publishes one no-force merge commit to the explicit checked-out target only while a Git reference-transaction hook proves that target still has the expected old SHA. Postchecks use one pinned published SHA and confirm the final target ref. Added paths are preflighted and Git's merge safety remains authoritative, so ignored local files are not overwritten. Repository scripts are never executed. Source conversation worktrees are never the integration workspace. After a successful train landing, the coordinator auto-pushes the target branch to origin with the same no-force policy. A push failure does not undo the landing or block later trains; the local merge remains and the error is logged.

Published landing commits describe the work instead of exposing an internal train branch UUID. Ensync prefers meaningful non-internal subjects already present in the accepted snapshots; otherwise it derives a concise subject from the changed areas. The body lists the exact changed paths and carries an `Ensync-Landing: true` trailer used for safe shared-checkout reconciliation. The message is installed through a temporary Ensync-owned `prepare-commit-msg` hook inside the same private publication-guard directory; repository hooks remain disabled and `agent-worktree` still owns the guarded no-force merge.

If an item conflicts, the integrator may invoke only a catalog provider whose automatic-landing capability is explicitly `supported` and whose subscription authentication and containment boundary are verified. Codex, Claude Code, and Factory Droid currently satisfy that contract; every other provider remains explicitly discovery-only or unavailable for this mutation path until its ordinary runner is promoted and the same landing profile is verified. The originating provider is tried first, and each subsequent durable attempt rotates through the other connected resolvers. Resolver runs retain the provider/account-selected default model and request that provider's verified `max` reasoning effort; Ensync does not guess a cross-vendor strongest model ID because availability and organization policy differ by account. A resolver has no fixed wall-clock deadline: it continues while the provider reports activity until it resolves the conflict or fails, and only provider liveness safeguards, explicit cancellation, or Host shutdown may stop it. Canonical realpaths and the shared Git directory are verified before a resolver starts; the process must terminate, conflict markers must be gone, and files outside the reported conflict set must remain identical before the resolution is accepted.

An unresolved item returns to durable retry state and is automatically retrained after an exponential-style backoff of 1 second, 5 seconds, 30 seconds, 2 minutes, then 10 minutes for every later attempt. The exact saved SHA remains anchored, retries continue until resolution or Host shutdown, startup immediately resumes journaled retry entries, and a new completion may wake older retries while later compatible items remain free to land. A failed resolver's temporary worktree is discarded before another provider sees the conflict. Attempt count never authorizes `git checkout --ours`, `git checkout --theirs`, a force merge, or any other whole-side substitute for a semantic resolution. Production delivery has no manual review state, filesystem repository lease, or environment opt-out; the only user alternative is the pre-run Protected branch only destination described above.

## Repository creation

Ensync isolates every local agent run in a Git worktree, so a focused project that is not inside a repository cannot host one. Rather than refusing that project, Ensync Host creates what the run needs: `git init --initial-branch=main` in the project folder, then one `Initial commit` holding the files already in it. A folder that is already inside a repository is never re-initialized; a repository that exists with no commit gets only the missing first commit, made at that repository's own root so a partial tree is never committed into it. The commit uses the computer's configured Git identity and falls back to an Ensync identity only when Git has none. Nothing is pushed.

Creation runs automatically before local isolation, and the Git panel also offers it explicitly whenever status reports the focused project outside a repository. A host can keep the previous fail-closed behavior with `ENSYNC_AUTO_INIT_GIT=0` (or the `autoInitializeGitRepositories` host option); a non-Git project then refuses local agent execution with an explanation instead. A home directory is always refused as too broad to become one project repository, and remote SSH execution still requires a repository that already exists on the remote.

## Repository import

- Import requires an allowlisted HTTP, HTTPS, SSH, or Git-protocol URL, a strict `user@host:path` SSH location, or an absolute local repository path.
- Relative repository paths, credentials embedded in HTTP URLs, `file::`, `ext::`, unknown external remote helpers, control characters, and option-like locations are rejected before Git starts.
- The destination must be an absolute path for a new folder whose parent exists. Ensync canonicalizes the parent, rejects filesystem roots and existing destinations, and enforces configured host project roots.
- A successful clone is inspected by Ensync Host and becomes the focused project using the canonical path returned by the filesystem.

## Status and connection

Status is derived from real Git commands and reports the repository root, checked-out branch or detached state, configured upstream, exact ahead/behind counts when Git has them, dirty state, changed-file count, and configured fetch/push remotes. The production branch is discovered from the selected remote's symbolic HEAD, then `main` or `master` remote refs; otherwise it remains unknown until the user supplies it.

Remote verification runs `git ls-remote --symref` non-interactively against the selected configured remote. It uses only credentials already available to Git. Ensync reports the connection as verified only after that command succeeds. Before verification or push, every configured URL for the selected remote is checked against the same location allowlist so a repository-configured external helper cannot execute.

## Push policy

The default mode pushes the checked-out non-production branch to the same branch name on the selected remote and sets its upstream. If the checked-out branch is the discovered production branch, safe mode refuses the push and asks the user to switch to a feature branch or use the guarded production flow.

Direct production push sends the current commit to the chosen production branch without force. It requires all of the following in both UI and host request:

1. Explicit production mode.
2. A valid production branch.
3. The server-side `allowProduction` flag.
4. The exact typed confirmation `PUSH TO <branch>`.

Push means a Git branch update, not a guaranteed deployment. It may trigger deployment only when the remote repository is configured to deploy from that branch.

Tests must use temporary local repositories and bare remotes. They must never push a real external repository.
