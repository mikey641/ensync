# Product distribution

For daemon lifecycle, a durable automatic-landing `retry` entry is terminal for the current active attempt: it remains recoverable in the journal but does not keep the daemon alive or poll. The next Host startup or repository completion retrains it. Thus “all work is terminal” below includes durable retry state, not only successful landing.

The public Ensync product site lives in `site/` and is deployed from that directory to the Vercel project `ensync`. Its public production URL is `https://ensync.vercel.app`. The site includes landing, product documentation, support, privacy/billing, and responsive light/dark pages.

The landing page uses a conventional marketing layout: a standard top navigation, a centered hero, and clean content sections. It no longer uses the persistent product sidebar, chat composer, prompt suggestions, or the interactive no-execution preview. Inter is self-hosted from `site/public/fonts/` so headings and body copy render at comfortable, readable sizes without a third-party font request. Copy emphasizes provider-neutral continuity, supported subscription routing, tabs outside an editor, safe pre-mutation fallback, automatic landing, delivery, remote execution, and mobile control without claiming that discovery-only providers can run. `site/public/og.png` is the matching social card, and the homepage owns absolute Open Graph/X metadata for the canonical production URL.

Downloads fail closed through separate verified channels. The macOS button uses `site/public/releases.json` and is enabled only when the latest version exists, its platform record matches, its real HTTPS artifact and SHA-256 are present, and signing plus notarization were actually verified. The Windows button first checks `site/public/site-config.json` for an exact `https://apps.microsoft.com/detail/...` listing after Partner Center certification; when no Store listing is configured it falls back to the stable release manifest and accepts only a signed, SHA-256-verified direct Windows installer. It must never expose an uncertified AppX, private package-flight URL, placeholder, or unsigned local artifact.

The production manifest is the direct macOS update feed. Updates check automatically in the background at startup and hourly, and a newer verified release downloads automatically; opening the installer remains an explicit user action. The app shows `app.getVersion()` and exact phases; it never installs, quits, or restarts itself. A packaged app must first verify its own native signature. A candidate must be newer and pass the same manifest gates as the site. Download progress uses actual received bytes and shows a percentage only with a real total. The completed artifact must match SHA-256 and the installed Developer ID, then pass Gatekeeper assessment. Only then may an explicit action open it. A Windows Store install is detected through Electron's Store context and instead exposes a non-interactive `managed` update state; it never queries Ensync feeds or enables channel/install controls because Microsoft Store owns updates. Development, unsupported, unsigned, unconfigured, stale, invalid, and unverifiable states fail closed.

The native wrapper lives in `desktop/`. Electron starts or reuses one bundled Ensync Host daemon on an ephemeral loopback port but serves every native window from the stable, privileged standard `ensync://app` origin. The daemon uses a user-only atomic rendezvous descriptor, random bearer token, renewable main-process owner leases, and checksummed bounded job and landing journals. Electron quit/update releases its shell lease without killing active provider or landing work; once all work is terminal and every lease is gone, the daemon persists final state and exits after a short grace period. A later shell reclaims the same daemon or starts a new one over the journals, returning terminal results idempotently, resuming queued landing items, and reconciling orphaned non-terminal provider work without replay. `Cmd/Ctrl+N` and File → New Window create a clean independently usable `BrowserWindow` in the same app process; they share only the Host and device-wide preferences, not conversations or workspace layout. The canonical window retains the historical unsuffixed v3 snapshot, while each new window receives an opaque main-generated UUID through authorized preload IPC before renderer hydration and uses UUID-namespaced v3 storage. The shell transactionally restores identities open at application quit, constructs canonical first when retained, and crash reload keeps the assigned identity. Manually closed identities are not restored while another native window remains, but their bytes stay archived; the last visible canonical window remains retained, and random non-reused UUIDs keep future windows clean without destructive cleanup. A closed retained project owner is reopened by its exact identity rather than copied into a new workspace. Mixed native versions fail closed instead of sharing canonical storage. Each window owns its crash-recovery budget and can invoke the narrowly authorized project picker and updater. A process-scoped `ENSYNC_WORKSPACE_RECOVERY_FILE` path optionally enables one fixed canonical-only recovery IPC: it returns only a bounded v3 envelope, which the renderer checksum-verifies and non-destructively merges before App hydration with a persistent idempotence marker. The application menu deliberately leaves `Cmd/Ctrl+T`, in-workspace `+`, and `Cmd/Ctrl+W` to the renderer, while `Cmd/Ctrl+Shift+W` closes only the focused native window. The custom protocol proxies only `/api` to that private Host, replaces renderer-supplied authorization and owner headers with main-process credentials, opens no second listener, keeps renderer Node access disabled, and retains CSP enforcement. The sandboxed preload exposes only fixed identity, recovery-candidate, directory-picker, and updater IPC calls plus one synchronous `webUtils.getPathForFile` wrapper that accepts an actual renderer `File` dropped by the user. It does not expose Electron, general IPC, raw storage keys, arbitrary path lookup, or filesystem reads. Native packages include the exact pinned `agent-worktree` helper under app resources. macOS packaging verifies and combines the pinned arm64 and x64 helpers into one universal executable; Windows stages the pinned x64 executable. No global installation is required. The package configuration targets a universal macOS DMG/ZIP plus Windows x64 NSIS/ZIP and explicitly includes the preload/picker/native-window/workspace/recovery modules. Native builds must run on their matching operating system.

A detached Host launch that does not produce a healthy descriptor before its readiness deadline must terminate and reap the exact child it spawned before releasing the cross-process launch lock. The renderer may then retry indefinitely without accumulating stalled Electron/Node bootstraps or exhausting process resources. A child that already produced and authenticated a healthy descriptor is preserved as the shared Host.

Local development installation is compare-and-swap, never a blind whole-app replacement from one conversation worktree. Copy the currently installed app as the staging base, apply only the exact reviewed files or `app.asar` entries, and run `npm --prefix desktop run verify:local-install-scope -- --base <base.app> --candidate <staged.app> --allow <exact-path>` once per permitted change. The verifier expands `app.asar` to entry-level differences and rejects broad, unused, or undeclared allowances. It also requires the candidate itself to contain the native titlebar/window-chrome markers plus queue-first submission, **Push now**, live-delivery behavior, and the parent-thread filter that prevents a subagent turn from replacing Push now's Codex precondition; it rejects the removed automatic `Steer the active Codex turn` composer path. A previously damaged base therefore cannot normalize another regression, even when the containing file was otherwise allowed. Immediately before the atomic swap, compare the captured base to `/Applications/Ensync.app` again with no allowances; any concurrent change aborts the install. Never modify or re-sign the live bundle in place: prepare and, when needed, sign the staged candidate while it is not executing, stop only the installed shell after confirming the detached Host can preserve active work, then atomically swap and relaunch. A palette task may not replace JavaScript, Host, native-shell, or layout assets, and a native fix may not replace renderer or Host assets. Keep a recoverable timestamped backup. Local unsigned development overlays are not public releases and must not be represented as signed or notarized.

A local continuous-update service (`desktop/scripts/continuous-update.mjs`, `npm --prefix desktop run continuous-update`) polls the repository's main branch for new commits and, when main advances, rebuilds the UI and copies changed host and UI files into the installed `/Applications/Ensync.app` bundle using the same guarded incremental-update logic as the manual `update-app.mjs` script. It records the last-seen commit in `~/.ensync/continuous-update-state.json` so it does not rebuild for the same commit twice. On first start it records the current commit without rebuilding, so launching the service never immediately kills the running app. Every incremental update entry point reads the durable landing journal before mutating the bundle and checks again immediately before a restart; this guard lives in the shared update primitive so continuous, manual, and one-shot invocations cannot bypass it. Any `queued` or `integrating` train defers the update, which retries after landing becomes terminal, and an existing unreadable journal fails closed instead of interrupting possibly active work. Relaunch targets only the argument-free Electron shell process; the detached Host uses a bootstrap argument and must survive UI replacement with its jobs and landing resolver intact. Durable retry entries remain terminal for this purpose and do not block updates indefinitely. The service overlays only interpreted source (host `.mjs` files and built UI assets) into an already-installed app; it never touches native binaries, code-signing, notarization, or the public release feed. Semantic versioning, signing, and the signed-tag release path stay completely separate. The service is a dev-loop convenience for getting landed work into the running app without a manual rebuild step, not a replacement for the public release pipeline.

The one intentional cross-window data exception is the native shell's neutral Recent Projects registry. It contains only bounded local project name/path/host records and is exposed through fixed per-window-authorized get/migrate/remember IPC plus a broadcast update. Active focus and all conversational workspace state remain private to the originating window namespace.

iOS and Android are first-class mobile app targets for remote agent execution through Ensync Sync. The Capacitor client and native platform projects live in `mobile/`; they reuse the conversation-first product model and established linked-mark artwork but do not embed Ensync Host or provider CLIs. The development client authenticates and pairs through Sync, accepts a Host project path, and submits/follows/stops/steers the Host-owned job through the end-to-end encrypted brokered channel defined in Remote runtime. Web assets build and synchronize into both native projects. Actual device/simulator compilation, App Store and Play Store packaging, platform signing, push-notification credentials, OS-backed secure key storage, background wake/reconnect behavior, mobile release manifests, and publishing remain unavailable until verified independently on both platforms.

The tag-triggered desktop release workflow preflights a public release repository, complete macOS signing/notarization, one complete Windows signing path (PFX or Microsoft Trusted Signing), and Vercel deployment credentials before building a full desktop release. It builds both platforms, verifies artifact size and SHA-256 against native attestations, and refuses a full public release unless Windows installer signing plus macOS app/DMG signing and app/DMG notarization are all verified. A manual `macos-only` dispatch runs the same preflight with only macOS signing/notarization, Vercel, and the public binary repository; it publishes only the signed, notarized macOS DMG and ZIP and records `platforms.windows` as `unavailable` because Windows is distributed through the certified Microsoft Store listing. Both paths create or idempotently repair the GitHub release, then deploy the exact generated manifest and site to Vercel using explicit project credentials. A failed site deployment leaves the previous feed in place and the workflow can be rerun safely. The desktop package uses the established Ensync linked-mark icon. Local unsigned builds are test artifacts only. The currently built macOS files are unsigned and unnotarized, so the public macOS manifest remains unavailable until the Apple signing and notarization credentials are activated.

## Release lifecycle

Active product development stays separate from public distribution. Preparing this lifecycle does not authorize creating remotes, adding credentials, tagging, signing, publishing, or deploying.

1. Development builds are local test artifacts. Every packaged build carries its exact semantic version, source commit, dirty-worktree flag, build time, and `dev` channel identity so a report can identify the bytes under test. Unsigned development builds continue to fail closed for native updates.
2. Beta is an explicit opt-in update channel with its own HTTPS manifest. Prerelease tags may update only the beta feed and must never replace the stable site download or stable update feed. A manual macOS-only beta dispatch may update the beta feed with a prerelease macOS build while Windows remains unchanged.
3. Stable is the default channel. A stable tag may update the stable feed as a full desktop release only after both native builds, signatures, notarization, checksums, and attestations pass; a manual macOS-only stable dispatch may update the stable feed after the macOS build, signature, notarization, checksums, and attestations pass while Windows remains `unavailable` (Store-distributed). Stable releases never contain prerelease versions.
4. Each channel retains prior verified manifest metadata and release artifacts. Rollback changes only that channel's manifest pointer to an already-published, still-verifiable installer; it does not rebuild artifacts, mutate user data, or silently install anything.
5. Fixes move through one repeatable loop: identify the exact build, reproduce, add a regression test where possible, fix, run full verification, publish to beta after credentials are intentionally activated, confirm the installed beta, then promote through a separately verified stable release.

The source is MIT-licensed under `LICENSE` and may be published openly. Public DMG/EXE/ZIP assets still live in a separately configured public GitHub releases repository, accessed by a dedicated least-privilege release credential. A source-repository tag identifies the source revision; release manifests and native attestations record that revision. The workflow must verify the configured binary repository is public before it creates a release.

Stable and beta use separate feed files at the same production origin. Deploying one channel must preserve the other channel's last verified feed. Existing stable clients remain compatible with the additive manifest fields. The updater checks that a feed's declared channel matches the user's selected channel, rejects prerelease versions on stable, and clears any downloaded candidate when the channel changes.

Conversation, preference, workspace, and Host-journal formats remain backward-readable across an update. Every format change requires migration and recovery tests before beta. A release is not promoted while a prior supported build cannot open the migrated state or while rollback would strand the user's locally stored data.

Vercel SSO deployment protection is disabled for the public product site. Site validation is `cd site && npm test`; deployment is `npx vercel --cwd site --prod --yes` after review. Vercel's local `.vercel` and `.env.local` state is ignored and must never be committed.

The public privacy policy at `/privacy/` covers account identifiers, encrypted workspace sync, server- and device-hosted execution, selected AI providers and infrastructure processors, security, retention, user controls, deletion requests, and international processing. The public privacy and support contact is `mikey641@gmail.com`; changing that address requires reviewing the policy and both public pages together.
