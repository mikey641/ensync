# Workspace tabs

Each conversation has a stable ID independent of its open tab. History can reopen a chat without duplicating an existing tab. Closing a tab does not delete the conversation.

Closing the final open tab leaves the workspace empty instead of implicitly creating a replacement conversation. The empty workspace offers an explicit New conversation action, and the empty tab order/active selection persists across relaunch so history remains closed until the user reopens or creates a chat.

The native shell must keep the page origin stable so the versioned `ensync-workspace-snapshot-v3` commit remains available across relaunches. The Electron origin is `ensync://app`; the Host's private ephemeral port is an implementation detail and must never become the renderer's storage origin. Older `ensync-workspace-v2`, `ensync-split-layout-v1`, and `ensync-ui-visibility-v1` values are migration fallbacks only; the checksummed workspace snapshot is canonical.

Workspace recovery uses synchronous local-storage commits with primary, staging, and previous-version backup records. Each commit contains chats, open-tab order and active tab, conversation layout, split sizes/hidden/maximized state, drafts, hideable UI visibility, conversation-sidebar width, sessions, unread-completion state, execution-panel choices, bounded CLI-visible events, errors, and in-flight-run metadata. In-flight metadata includes the opaque Host job ID and last persisted non-terminal event sequence; the renderer synchronously checkpoints that reconnect key and pending user turn before the Host may start the provider. The renderer commits in a layout effect and flushes again on hidden/pagehide/beforeunload. A complete newer staging record is recoverable if promotion was interrupted, a corrupt primary falls back to the newest valid record, and the first restored render promotes the reconciled state. Recovery is limited to bytes synchronously written before the process ended.

Account chat sync is opt-in and separate from local workspace recovery. A configured Ensync Sync service accepts a normalized username and 12–256-character password; the service stores an scrypt password verifier, while Ensync Host derives a separate key and AES-256-GCM encrypts the account conversation document before upload. Non-loopback service URLs require HTTPS. The remote store receives only encrypted documents plus revision metadata; it never receives provider credentials, vendor sessions, source files, terminal output, queued work, active-job state, drafts, layout, or local attachment paths. The encrypted project reference may retain its last path as an unverified hint, but every computer must re-inspect a real local path before a synced chat can run.

The account document includes every conversation plus bounded neutral project references and converges by stable chat/message ID. Remote revisions use compare-and-swap; a conflict returns the newer encrypted document for one deterministic merge and retry rather than overwriting either computer. Completed delivery state wins over a stale pending copy, and any queued or pending turn arriving from another computer is imported as interrupted/non-resumable so sync can never execute or replay it. Background sync runs only for an authenticated visible workspace after local chat changes, on focus/network return, or a bounded visible poll. Login and the derived encryption key are currently Host-memory-only, so Host restart requires sign-in again; the UI states this explicitly and never fabricates a persistent session.

Persisted CLI event history is globally storage-bounded and retains the newest per-chat events with an explicit omission notice. This protects chats, tabs, drafts, and layout from terminal-output quota pressure without implying that omitted historical output was recovered.

Provider runs are Host-owned jobs rather than renderer-owned HTTP lifetimes. A renderer replacement or dev refresh reconnects the persisted opaque job ID, requests only buffered events after its last non-terminal sequence, and applies the retained terminal result idempotently; disconnecting a stream subscriber never cancels or replays the provider. If stale terminal presentation lost that reconnect key, startup may probe only deterministic recent job IDs for that exact turn/provider/attempt and adopt an exact running or completed match; it never replays the prompt or searches unrelated jobs. The native shell connects through an authenticated, user-only rendezvous record to a detached Host guarded by renewable shell leases. Ordinary renderer traffic reuses a healthy cached lease, the background heartbeat force-renews it, and a request arriving near or after expiry uses the authenticated claim endpoint before it is proxied. The app-protocol proxy resolves this authenticated endpoint for every API request instead of freezing the startup port. If the Host PID actually ended, concurrent windows share one fenced recovery promise that starts one journal-aware replacement before the next request; a live-but-busy PID remains protected through bounded health retries. This repairs missed heartbeats and genuine Host loss without changing the stable renderer origin or multiplying daemon traffic, so saved workspace hydration remains available. Host discovery reads atomic primary/backup descriptors and serializes daemon creation with a cross-process launch lock. It must never delete a live Host rendezvous or start a competing journal writer because one health check timed out. Journal payloads carry the owning Host instance/PID, reject reads or writes from another live instance, and batch noisy output checkpoints while keeping job registration, provider-start, and terminal events synchronous. Quitting and reopening the shell therefore reattaches to a still-running provider job, while the checksummed, prompt-free journal retains bounded redacted public events and terminal results across a later Host restart. Stop remains the only renderer action that cancels the exact job. If the Host process actually ended while a provider was still running, the journal marks that job `host_job_orphaned` instead of replaying it; if no retained Host job exists, or a legacy pending turn has no reconnectable job ID, the chat is marked `interrupted`. Both ambiguous cases discard the provider session, set `reconciliation_required`, and add one non-retryable terminal event without creating an unread-completion dot or alert. The desktop shell reloads a crashed renderer at most twice within 30 seconds; repeated crashes stop automatic reloads instead of looping. The policy is identical on macOS and Windows.

A visible renderer retries a failed Host/provider-status sample after one second and then uses bounded exponential backoff. This lets a just-replaced Host restore the Local host state without leaving the already-healthy app labeled offline or requiring a manual refresh; hidden windows retain the slower background cadence.

The persisted conversation-view preference has two explicit modes. **Open as tab** keeps every conversation open in a standard tab strip while showing only the active conversation. **Open in split pane** shows open conversations side by side. Existing persisted workspaces without this preference migrate to split mode so the established layout does not change.

In split mode, new panes are inserted beside the active pane by default. Users can choose chronological end placement; that secondary preference is retained while switching modes and persists locally.

Keyboard targets: new tab `Cmd/Ctrl+T`, jump/search `Cmd/Ctrl+K`, and close tab `Cmd/Ctrl+W` inside a workspace. The native desktop shell separately owns `Cmd/Ctrl+N` for **New Window** and `Cmd/Ctrl+Shift+W` for **Close Window**. The native menu must not register the renderer-owned new-tab or close-tab accelerators, and every in-workspace `+` keeps its existing adjacent/end placement behavior.

Manual renderer reload is available through View → Reload, View → Force Reload, `Cmd/Ctrl+R`, and `Cmd/Ctrl+Shift+R`. The renderer synchronously checkpoints workspace and in-flight reconnect metadata before unloading, then reconnects each Host-owned job by its opaque job ID and last event sequence without cancelling or replaying the terminal-backed provider run. A normal whole-app quit releases only the native shell lease: active Host jobs continue detached, completed results remain journaled, and the next launch reclaims the same authenticated Host or restores its journal. Only an actual Host/process or machine failure during provider execution becomes reconciliation-required.

Source-tree desktop launches use a detached Electron launcher, so `npm --prefix desktop start` and `npm --prefix desktop run open` do not inherit the lifetime of a temporary terminal or agent PTY; foreground diagnostics remain available through the explicit `start:foreground` script. An abruptly closed legacy renderer-owned stream is classified as interrupted and reconciliation-required, including migration of the exact historical `Ensync Host returned a malformed execution event.` failure when no retained Host job exists. A complete newline-framed event containing invalid JSON remains a genuine malformed-stream error.

The desktop app is single-process but multi-window. New Window creates another top-level `BrowserWindow` at the same stable `ensync://app` origin and on the same private Ensync Host; it never starts a competing Host. Each native window receives a main-process-generated opaque UUID through one authorized preload IPC call before React imports or reads storage. The first/canonical window keeps the existing unsuffixed v3 primary/staging/backup and legacy migration behavior unchanged. Every New Window starts clean and derives a distinct namespaced v3 key set from its verified UUID; it never reads, clones, or overwrites canonical or another window's chats, tabs, drafts, active project, queues, or layout. Native windows share only the shell-owned neutral Recent Projects registry described in Project focus, plus the existing Host and device-wide preferences. A renderer-controlled URL or raw storage key cannot choose the identity.

The workspace-identity IPC handler is a single idempotent main-process registration installed synchronously before updater initialization and asserted again before any `BrowserWindow` is constructed. Authorization requires the exact live registered `webContents` and trusted `ensync://app` frame origin; the handler remains available across activation, New Window, crash reload, and all current/future windows, and teardown cannot remove it while a registered window remains. A workspace identity cannot be opened in two native windows concurrently. Mixed native versions fail closed: an Electron renderer with an older preload or a missing identity handler requests a full quit/reopen instead of ever claiming the unsuffixed canonical namespace. Browser development without Electron remains canonical.

The native shell transactionally retains the identities of windows open at application quit and restores those independent workspaces on the next app launch while reclaiming the surviving authenticated Host or starting one replacement. Relaunch always constructs canonical first, regardless of last-focused ordering, so the historical unsuffixed workspace is the original window and UUID-scoped windows remain secondary; after all retained windows exist, it brings the last-used retained identity to the front so a clean secondary window cannot make the user's saved historical chats look missing. Other windows remain open and independently selectable. The canonical identity is always retained so closing its window beside an isolated one cannot orphan it. Closing an isolated window while the app remains open discards that identity from relaunch restoration, but its checksummed localStorage bytes remain archived; a future New Window receives a new UUID and therefore still starts clean. During canonical hydration, bounded recovery may read retired, non-retained snapshots without altering them. Neutral recent projects recover independently. Full project-scoped history—chats, tabs, drafts, sessions, errors/events, queues, and opaque Host-backed in-flight metadata—is imported only when canonical has no meaningful history for that normalized project path; current canonical state, selection, settings, and unrelated projects win. Source-revision markers make the current-first merge idempotent, and recovered Host work is reattached only by exact job ID without prompt replay. Isolated and browser workspaces never absorb archived history. Windows last-window quit retains the final workspace, matching normal platform quit behavior. A renderer crash reloads the same `BrowserWindow` and therefore reuses the exact identity and snapshot. Each window still owns its focus lifecycle, project-picker/updater authorization, and bounded crash-recovery guard.

Selecting a different project must preserve a native window that already contains meaningful messages, drafts, queued prompts, execution records, continuations, or in-flight runs. The renderer refreshes the shell-authenticated retained-workspace roster immediately before routing so windows created or closed after startup are recognized. If another live retained window owns durable history for the target project, one authorized main-process IPC focuses that exact registered window and asks it to re-inspect and select the project. Otherwise, the shell creates a new isolated native window and attaches a validated one-shot project launch containing the target path and source workspace identity. The new window checksum-reads a bounded set of canonical, retained, and retired workspace snapshots and selects the strongest meaningful history for the exact normalized target path; this covers a manually closed isolated window and a retained canonical identity whose native window is currently closed. A fresh `New conversation` has zero recovery score. Only the selected project's chats, tabs, chat-scoped drafts, sessions, errors/events, queues, in-flight metadata, and filtered split layout are copied into the new namespace; every source namespace remains byte-for-byte untouched. If no meaningful source exists, the target opens honestly empty, and failure to create the window leaves the source project open. A fresh current window with no meaningful history may still switch in place, but before creating any blank chat it must run the same bounded exact-project recovery selection, commit the recovered scoped state into its own namespace, and activate a recovered tab (or a stable tab for the first recovered chat). Every target path is re-inspected by the Host, and Windows path matching remains case-insensitive.

An operator-selected crash-recovery artifact can be supplied only at native process start through `ENSYNC_WORKSPACE_RECOVERY_FILE`. The fixed preload IPC returns at most one bounded, structurally valid v3 envelope and only to the authorized canonical window; the renderer then verifies its checksum before hydration. Recovery is a deterministic current-first merge: current chats, projects, active selection, settings, drafts, queues, tabs, and live in-flight metadata win; historical projects merge by path; genuine ID collisions receive deterministic remaps propagated through every chat/tab-scoped record; and recovered pending runs become interrupted/reconciliation-required instead of replaying. Recovered conversations and tabs append to current state, the previous current primary becomes the transactional backup, and the external artifact remains unchanged. A persisted SHA-256 artifact marker makes repeated launch idempotent. Isolated windows cannot read or apply canonical recovery.

An explicit native process-start import can add one Codex JSONL session to one exact shell-issued workspace UUID. It requires rollout, `history.jsonl`, canonical target-project, target-workspace, and exact `IMPORT CODEX` environment values together; every other window receives nothing. The main process read-only snapshots bounded file prefixes after `fstat`, so an actively growing source yields a stable hashed prefix and an incomplete final line is excluded rather than guessed. Only non-empty `history.jsonl` text for the exact session and top-level Codex `response_item/message/assistant` `output_text` are eligible. Reasoning, system/developer and injected user context, compaction, subagent/inter-agent records, tool calls/results, execution events, tokens, hidden metadata, binary image data, and recognized credentials are excluded. The renderer maps the chat to the canonical project path, deterministically merges source-owned message IDs, preserves unrelated chats/layout/drafts, collision-remaps unrelated IDs, opens/unhides the one imported tab, marks the historical response read, and commits through the existing checksummed v3 staging/backup/primary transaction. Repeating the same prefix is a no-op; a later longer prefix adds only new message identities. Source files are never written.

Every visible normal-tab header and every visible split-pane header owns a `+` action. With adjacent placement, that action inserts the new conversation immediately after the exact header clicked, even when it was not active; with end placement, it appends chronologically. The new conversation becomes active without changing the identity or ordering state of existing tabs. Global new-conversation entry points continue to use the active tab as their adjacent anchor.

Open conversations can be reordered from either header system. Mouse users drag a normal tab or split-pane header and drop before or after another visible header; a clear insertion marker follows the pointer. Keyboard users focus the tab title and press `Alt+Shift+Left/Right` to move it one visible position. Reordering changes only the persisted `WorkspaceTab[]` order: stable tab/chat IDs, the active conversation, and split presentation state keyed by tab ID (width, hidden, and maximized state) remain unchanged. Header action buttons never start a reorder, and finishing or cancelling a drag clears all drag/drop state without triggering split-pane double-click maximize.

Split view treats each open tab as a resizable conversation pane. Pane width, hidden state, and temporary largest-pane selection are presentation state keyed by stable tab IDs; they never duplicate or delete the underlying conversation. A hidden-pane shelf makes every hidden tab recoverable. Double-clicking a pane header makes that pane the largest while every other visible pane stays mounted in the row and remains available through horizontal scrolling; all panes are not required to fit in the viewport at once. The selected pane reserves at least two normal pane widths and roughly two thirds of the visible split viewport so sibling minimum widths cannot defeat the largest-pane presentation. Because sibling minimums lay the enlarged pane out past the viewport's right edge, making a pane largest also scrolls the split viewport the minimum distance that brings that pane fully into view, and keeps it fully visible while the viewport or pane row resizes; siblings scroll out to the left instead of the enlarged pane rendering half empty and half clipped at the window edge. A manual horizontal scroll is preserved whenever the enlarged pane already fits in view. Double-clicking it again restores the persisted divider proportions. The legacy `maximizedTabId` snapshot field remains for compatibility but must not produce a full-workspace pane. Normal-tab mode ignores split-only hidden/largest presentation while active without erasing that state.

The task-finished treatment is an unread-completion marker, not a permanent record that an agent once responded. It appears only when the latest message is a newly completed agent response the user has not opened, disappears while a new run is working, and is absent for new or failed-only conversations. Activating a normal tab, clicking or focusing a split pane, or restoring a hidden pane records that exact completed message as read and clears the treatment; a later background response creates a new unread marker. Read state is keyed by stable chat ID and the exact completed agent-message ID in `ensync-workspace-v2`, so it survives relaunches and tab close/reopen without mixing concurrent chats. Hidden panes retain their unread treatment until they are actually restored and activated.

Settings persist one device-local task-finished style: the compact green dot is the backward-compatible default, Green header tints only the unread tab or pane header, and Whole tab tints and outlines the unread conversation pane while using the stronger green treatment for normal and hidden tabs. All styles expose the same accessible completion status and reserve dot layout space only in dot mode. Tab headers never restore the unrelated decorative provider-color dot.

Working state is keyed by stable conversation ID rather than held as one workspace-wide lock. Multiple split panes may run at the same time, while an atomic per-chat guard prevents duplicate submits in the same conversation even before React renders the pending state. Drafts, errors, CLI event streams, sessions, fallback attempts, completion dots, and completion alerts remain scoped to their originating chat. Closing, hiding, resizing, maximizing, or reordering a tab does not cancel or redirect its run; closing a tab never deletes the underlying conversation, so its result is available when reopened.

Every active chat shows a real elapsed label such as `• Working (27s)` below one minute and `• Working (16m 23s)` for longer runs, calculated from that chat's immutable `inFlightRuns.startedAt` timestamp and refreshed near each elapsed-second boundary. Concurrent panes keep independent clocks, and completion, failure, or cancellation removes the label immediately. Crash reconciliation clears in-flight metadata before rendering, so an interrupted restored run never resumes a cosmetic timer. The changing number is visual-only; assistive technology receives one static per-run working description instead of a live-region announcement every second.

Sending again while one local Codex chat is working uses the retained app-server job's `turn/steer` operation when no FIFO tail already exists. The Host binds delivery to the exact active provider turn ID, validates attachments again, and makes the correction another visible user message in the same logical turn; completion updates every user message in that turn and advances the synchronized session cursor by all delivered steering messages plus the one agent reply. A renderer must never infer push eligibility from a retained job ID or generic running state: Ensync Host emits explicit ready and closed transitions around the real provider turn, and only that observed readiness exposes the text-labeled **Push now** action. An unlabeled send arrow or internal `steer` terminology is not sufficient user-visible affordance. If the Host proves the active turn rejected or could not receive the message, Ensync safely falls back to the persistent FIFO. A safe end-of-turn race stays queued without an error banner; an unconfirmed delivery is never queued again because that could duplicate execution. Claude, SSH, unsupported/older Codex app-server jobs, and sends behind an existing FIFO tail continue to queue.

When another renderer tries to start a different turn for a conversation workspace already owned by a live Host job, Host admission returns that exact occupied owner before creating a second retained job or provider process. The new message becomes a normal persistent FIFO entry. A native **View active run** action appears only when the Host owner metadata and shell-authenticated live-window roster identify the same exact project, chat, and job; the target renderer verifies those bindings again before focusing and activating the conversation. A cross-window **Push now** hands the stable FIFO message to that verified owner renderer idempotently, which persists it before using the existing exact-job steering path; only then does the source retain a visible but non-executable `transferred` copy. Confirmed delivery joins the active logical turn, a proven rejection stays queued, and ambiguous delivery becomes interrupted and non-replayable. Saved snapshots, generic running state, PIDs, and job IDs without the full binding never authorize navigation or steering. Owners in another Host process may be described factually but cannot be focused, steered, stopped, or reclaimed by the current Host.

When the latest completed agent reply names another protected `ensync/chat-…` branch or a protected workspace/worktree ID, Ensync may offer **Open owning conversation** only if the reference uniquely resolves to one different chat in the current renderer's live state or the checksummed snapshots of other shell-retained native workspaces. `ensync/chat-` prefixes require at least six hexadecimal characters; a shortened ID labelled as a workspace, worktree, or conversation requires at least four, covering provider copy such as `0f96… workspace` without treating arbitrary short hashes as navigation. A same-window target is activated locally; a cross-window action carries the exact workspace, project, normalized local path, and chat coordinates through the authenticated native focus bridge, and the target renderer verifies that binding again before selecting the chat. This is navigation only: it never opens or mutates the other worktree, transfers a draft, queues or sends `continue`, resumes a provider, or weakens the live-roster proof required by active-run controls. Ambiguous, corrupt, stale, unretained, current-chat, and browser-only references show no action.

Same-Host occupied authorization carries the predecessor turn ID only in the owning Host process's live memory; filesystem owner records, job journals, provider requests, and cross-Host descriptions never retain it. The native shell exposes an exact boolean roster-match query rather than a job listing, and View/Push/Stop remain hidden until both that query and the exact Host job probe succeed. Target handoff persistence must succeed synchronously before ACK. If an ACK is lost, the shell may redeliver only the original same-source/action/content request; the target's local immutable message tombstone acknowledges queued or consumed duplicates without repeating Push/Stop. Stop approval exists only in the target-bound payload, so rejection or timeout cannot make the source FIFO executable. A handoff racing any exact local terminal outcome becomes ordinary target FIFO state; the existing success/review gate still decides whether it may run.

Where live steering does not exist, the queue head instead offers the explicitly destructive **Stop & send now**, and never under the Push now label: it ends the running turn, discarding its in-progress work, and immediately runs that one queued message. It appears only while live steering is genuinely unavailable for the running turn — a steerable Codex turn shows Push now instead — and only while the head still binds to the running turn's exact logical predecessor, project, and execution target. The control is two-step: the first press arms a distinct **Confirm stop & send** label that disarms itself after a few seconds or as soon as the action stops being available. Confirming records the same explicit persisted approval as **Run next message anyway** before stopping, so the stopped predecessor is never retried and only the head advances; a plain Stop still pauses the tail. The status card names the cost of the action next to the reason the provider cannot take a mid-turn instruction.

Queued sends append an immediately visible `queued` user turn to that chat's persistent FIFO and never start a second provider process for the same conversation. Provider mode/preferred provider, provider-neutral size, fallback enabled/order, Auto Context choice, canonical project identity/path, and exact execution-target key are snapshotted when the prompt is queued. Provider connection/usage is checked live only when that turn reaches the head. A changed target or unverified project pauses the head rather than substituting the current computer. Each queued run compiles against the newly completed logical transcript and current matching vendor session at execution time, excludes its own and all later queued prompts from provider input, inserts its reply before later queued turns, and advances the session cursor by executed messages only.

Automatic queue advancement is success-only: the predecessor user turn must be `completed` and have its matching agent reply. Failed, stopped, interrupted, reconciliation-required, missing, or ambiguous predecessors leave later prompts visible and paused across relaunch.
